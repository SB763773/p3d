## 2026-11-08 · 本地推理引擎：不需要任何账号也能真生成

上一轮把云端后端搭完，但**卡在实名认证**：腾讯云个人认证要求满 16 周岁，过不了。
整个项目的最后一块短板就是这个 —— 代码全通，只差一个密钥。

这一轮换了个思路：**既然模型本身开源、显卡在手，为什么还要绕道平台**。

### 先探测硬件，再决定方案

不猜，直接查机器：

| 项         | 实测                                                                                 | 结论                                                   |
| ---------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 显卡       | NVIDIA RTX 5060 Laptop，8 GB，**compute_cap 12.0**                                   | 够跑 TripoSR（门槛 6 GB）；但 sm_120 对 torch 版本很挑 |
| CPU / 内存 | i7-13700HX 16 核 / 15.7 GB                                                           | 够                                                     |
| 网络       | 单连接 0.4 MB/s；**8 线程并行 3 MB/s**                                               | 关键发现，见下文                                       |
| 可达性     | `hf-mirror` 与 `modelscope` 通，`github` 慢但通；`huggingface.co`、`python.org` 不通 | 权重与代码都有路，但要挑源                             |

### 三条路的可行性

| 路线                            | 判断                                                                |
| ------------------------------- | ------------------------------------------------------------------- |
| 国内云 API（混元等）            | 全部要求实名 → **排除**                                             |
| 海外 API（fal / Tripo / Meshy） | 要国际信用卡；Tripo 免费档还禁商用、Meshy 免费档不能下载 → **排除** |
| 本地跑开源模型                  | TripoSR 是 **MIT**、6 GB 显存 → **可行**                            |

### 交付

| 模块                                      | 内容                                                                    |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| `local-engine/inference.py`               | TripoSR 推理封装：预处理、显存不足自动降档（256→224→192→160）、GLB 导出 |
| `local-engine/engine.py`                  | FastAPI 服务，串行任务队列，五个薄接口（health / jobs / glb）           |
| `local-engine/tsr/`                       | 原仓库源码（MIT），只改了两处，都留了注释                               |
| `local-engine/selfcheck.py`               | 环境自检：CUDA 实跑、mcubes 后端、GLB 导出、权重完整性、模型加载        |
| `server/providers/local.ts`               | node 侧 provider，把引擎接进既有 `/api` 契约                            |
| `scripts/engine.mjs` / `engine-setup.mjs` | 启动与一键安装（含断点续传、国内镜像）                                  |

前端**一行没改** —— 它只跟 `/api` 说话，`local` 和 `hunyuan` 在 `/api/health` 的
`providerReport` 里区分。

### 四处必须改，否则 Windows 上跑不起来

| 问题                                                     | 处理                                                                                                      |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `torchmcubes` 要 CMake + MSVC 现场编译                   | 换成 `PyMCubes`（`tsr/models/_mcubes_compat.py`），接口一致，PyPI 有预编译包                              |
| `rembg` 在 `utils.py` 顶层 import，拖 200 MB onnxruntime | 改成函数内延迟导入：前端已去背景，正常路径根本走不到                                                      |
| **RGBA 直接喂会报维度错**                                | ViT 的 `patch_embed` 是 `Conv2d(3, …)`，而 `ImagePreprocessor` 只缩放不管通道。必须把透明区合成白底转 RGB |
| RTX 50 系（sm_120）装旧轮子会"能初始化但一算就炸"        | 锁 `cu128`。**PyPI 上 Windows 的 torch 是 CPU-only**，CUDA 版只能从 PyTorch 源或国内镜像拿                |

第三条是查代码才发现的 —— 原版 `run.py` 里传的是 RGBA，看着能跑，但那是靠
代码路径里某处恰好转了 RGB。我们不赌这个，在 `_prepare` 里显式合成白底。

### 网络这件事值得单独记

- 单连接 **0.4 MB/s**，但 8～12 段并行能到 **3 MB/s**，快 7.5 倍。所以 `engine-setup.mjs`
  里权重用 `curl -C -`，torch wheel 用分段并行拉再合并。
- 阿里云有 `mirrors.aliyun.com/pytorch-wheels/cu128/`，是**平铺的 wheel 列表**，
  用 `--find-links` 指过去即可，比 `download.pytorch.org` 靠谱。
- 权重走 `hf-mirror.com`（`HF_ENDPOINT` 必须在 import transformers 之前设，
  晚一步它就去连 `huggingface.co` 挂住 30 秒）。

### 这一轮踩的坑（都不是看文档能预知的）

| 坑                        | 现象                                               | 根因                                                                                                                                                         |
| ------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pymcubes>=0.1.12` 装不上 | pip 报 no matching version                         | PyMCubes 最新是 **0.1.6**，我按 0.1.12 写错了                                                                                                                |
| `import pymcubes` 失败    | ModuleNotFoundError                                | 包名 `PyMCubes`，**import 名是 `mcubes`**                                                                                                                    |
| regex 装得上但加载不了    | `DLL load failed ... 应用程序控制策略已阻止此文件` | Windows **Smart App Control** 拦了 `_regex*.pyd`。降级 2024.11.6 能过，但 **transformers 5.x 硬性要求 regex>=2025.10.22** → 只能把 transformers 一起降到 4.x |

第三条最费时间：报错信息指向 DLL，看不出跟 transformers 的版本约束有关。所以现在
`requirements.txt` 里把 `transformers<5` 和 `regex==2024.11.6` 一起锁住，`selfcheck.py`
也单独加了这项检查。

### 校验

全部本机实测，不是"应该能跑"：

| 项                           | 结果                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------- |
| `selfcheck.py`               | 全通过：torch 2.10.0+cu128、sm_120、CUDA 算子实跑、pymcubes、GLB 导出、权重 1.56 GB 完整 |
| 模型加载                     | **9.5s**，加载后显存剩 5339 MB                                                           |
| 进程内生成                   | **19.5s**，83,244 顶点 / 166,484 面，GLB 3.18 MB，回读一致                               |
| 引擎 HTTP 全流程             | 提交 → 轮询 → 下载 **24.3s**，GLB magic = `glTF`                                         |
| **BFF 端到端**               | **16.7s**，经 `/api/jobs/:id/model` 转发下载 3,330,704 字节，`glTF`                      |
| 成本记账                     | `estimatedYuan: 0, charged: false` —— 本地推理不计费                                     |
| tsc / biome / vitest / build | 全过，**144 个用例**（新增 11 个 local provider 单测）                                   |

注：BFF 那次 16.7s 比引擎直连的 24.3s 快，是因为它跑在同一进程的第二次生成上，
CUDA 上下文与 kernel 已经预热；首张图要额外付一次初始化开销（约 5–8s）。

### 未做

- 纹理烘焙：现在只有顶点色。要走 `bake_texture.py` 得装 xatlas + moderngl，
  而无头服务里创建 OpenGL 上下文容易崩。对"能转着看"够用，先不碰。
- 并发：任务串行。8 GB 卡没有余量跑两个任务，排队比 OOM 崩掉体面。
- 本地模式下 `quality` 档位不影响结果（本地没有极速版/专业版之分），只影响前端显示。

## 2026-11-01 · M5：简单模式（主界面收成"选图→生成→下载"）

后端骨架搭完后回头看前端：完整模式塞了太多"只有摆场景才用得上"的东西 ——
场景对象列表、移动/旋转/缩放 gizmo、网格线框、PBR 与面数。
第一次用的人面对这些只会卡住，他只是想把一张图变成模型然后拿走。

### 做法：加一层模式开关，而不是另写一套界面

| 文件                                                              | 作用                                                                            |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `src/lib/uiMode.ts`                                               | 模式的纯逻辑：解析/序列化、`resolveSceneAction`（新模型是"并排 / 替换 / 跳过"） |
| `src/store/useUiStore.ts`                                         | 记住模式选择，存在 `p3d:ui:v1`                                                  |
| `src/app/App.tsx`                                                 | 顶部「简单 / 完整」切换；按模式收起进阶区块                                     |
| `ViewerToolbar` / `SceneCanvas` / `useSceneHotkeys` / `JobResult` | 各自的进阶入口按模式隐藏                                                        |

**默认给简单模式**，且它不是删代码，只是把控件收起来 —— 切回完整随时能拿回来。

|                                               | 简单模式               | 完整模式     |
| --------------------------------------------- | ---------------------- | ------------ |
| 场景对象列表 / 历史记录                       | 收起                   | 显示         |
| 移动 / 旋转 / 缩放 gizmo、快捷键 G/R/S/Delete | 停用                   | 可用         |
| 网格 / 线框                                   | 收起                   | 显示         |
| PBR / 面数                                    | 收起（用默认档）       | 可调         |
| 再生成一次                                    | **替换**场景里那个模型 | 并排再摆一个 |

最后一行是关键：简单模式下场景永远只有一个模型。
否则"再生成一次"会堆出三四个一样的，还得手动删 —— 那一点都不简单。

### 顺带修掉一个真 bug（冒烟逼出来的）

切换界面模式时，场景里会**凭空多出一个一模一样的模型**。

根因：自动入场景的 `useEffect` 依赖里带了 `placeModel`，而 `placeModel` 依赖 `uiMode`。
切模式 → 回调换引用 → effect 重跑 → 又把当前任务摆了一次。
改成用 `placedJobRef` 记住"哪个任务已经摆过"，只认任务 id 第一次成功。

> 这类 bug 靠读代码很难发现，是冒烟里"场景状态已持久化"和"拖动 gizmo"两项同时挂掉才暴露的
> （多出来的模型让自动取景把相机推远，gizmo 手柄跑出了拖拽脚本的扫描范围）。

### 校验

- `tsc` / `biome`（0 error）/ `vitest` **133 用例**（新增 `uiMode` 8 个）/ `vite build` 全过
- 冒烟 **23/23**：新增「简单模式隐藏场景对象列表」「隐藏网格/线框」
  「简单模式下场景始终只有一个模型」「一键切到完整模式」四项，
  原有的 M4 摆放能力改成切到完整模式后验证

### 未做

- 简单模式下「重新生成」需要先清掉当前图，是一次多余的点击；想省掉的话要改 uploader 的重置时机
- 模式偏好只存本机，换设备不会同步

## 2026-11-01 · M2 骨架：把真实后端接上（只差密钥）

上一轮把闸门放到了服务端，这一轮把"真会花钱"的那一段也搭完。目标：**前端 → /api → 服务端 → 腾讯混元生 3D**
整条链路的代码全部到位，只差在环境变量里填密钥。

### 交付了什么

| 模块                          | 内容                                                        |
| ----------------------------- | ----------------------------------------------------------- |
| `server/providers/hunyuan.ts` | TC3-HMAC-SHA256 签名、提交/查询、档位映射、错误分类         |
| `server/providers/index.ts`   | provider 工厂：按环境变量选，没密钥就退回 mock 并说明原因   |
| `server/handler.ts`           | 新接口 `GET /api/jobs/:id/model`；成本改用上游实际结算值    |
| `server/types.ts`             | `ServerProvider` 契约补上图片本体与 `assetUrl` / `costYuan` |

### 接口依据（查过官方文档，不是凭记忆）

- 域名 `ai3d.tencentcloudapi.com`，版本 `2025-05-13`，服务名 `ai3d`，地域 `ap-guangzhou`
- 提交 `SubmitHunyuanTo3DProJob` / `SubmitHunyuanTo3DRapidJob`，查询对应 `Query...`
- 查询返回 `Status`（WAIT/RUN/FAIL/DONE）、`ResultFile3Ds`、`ResultCreditConsumed`
- 文件 URL 有效期 24 小时；**生成失败不扣积分**

### 几个关键决定

1. **档位怎么映射**：`draft` = 极速版（15 积分）；`standard` = 专业版 Normal（20）；
   `high` = Normal + PBR（30）。没用 LowPoly 当"高画质"——那是减面，反而更糙。
2. **上游地址不下发前端**：改成 `/api/jobs/:id/model` 由服务端转发。
   上游 URL 带签名且 24 小时过期，直接给前端既外泄凭据又受限于对方 CORS。
3. **成本以实际结算为准**：查询接口会返回 `ResultCreditConsumed`，
   用它覆盖事前估算，避免"估 2 元、实扣 3 元"的账对不上。
4. **密钥字段设为不可枚举**：`Object.defineProperty(..., { enumerable: false })`。
   日志和 `/api/health` 是密钥最常见的泄露口子，这样 `JSON.stringify`/`console.log` 都带不出去。
   这条是被单测逼出来的——测试里序列化整个 bundle，结果密钥就出现在字符串里。

### 顺带修掉的两个真缺陷（都不是本次目标，是跑冒烟时暴露的）

| 缺陷               | 现象                                                    | 根因与修法                                                                                                                                                                                                                 |
| ------------------ | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 画布整个消失       | `<canvas>` 被加上 `display:none !important`，只剩骨架屏 | drei 的 `<Environment preset>` 会去 `raw.githack.com` 拉 HDR，请求一直挂着 → 该组件永不 resolve → React 把整个 Suspense 内容隐藏。**等于"境外 CDN 连不上 = 3D 完全看不见"**。改成程序化光板（`<Lightformer>`），零外部请求 |
| `removeChild` 报错 | 控制台抛"节点不是子节点"                                | 加载态用了 drei `<Html>`，它把真实 DOM 挂到画布容器上；配合 React 19 的 Suspense 隐藏/恢复会挂到已失效的节点。改成 3D 占位盒                                                                                               |

> 第一个缺陷尤其值得记：它让之前那次 19/19 变成"运气好"——CDN 恰好可达。
> 现在整个应用**零外部网络依赖**（示例 GLB 也在仓库里）。

### 校验结果

- `tsc` / `biome`（0 error）/ `vitest` **125 用例**（新增 hunyuan 29、模型转发 6、工厂 7）/ `vite build` 全过
- 冒烟 19/19；并单独验证过 `GET /api/health` 会如实汇报"想用 hunyuan 但没密钥 → 退回 mock"

### 未做

- 真实生成仍未跑通：卡在腾讯云实名认证（需要手机号）
- 模型文件目前是"即取即转"，没有落到对象存储；上游 24 小时后失效，历史里的旧模型会取不回
- 并发控制：上游专业版默认 3 并发，我们这层还没排队

## 2026-10-25 · M3：把密钥和额度收到服务端（BFF）

对应方案 §8。M2 之前先做这层的原因：密钥一旦落到浏览器里，所谓"成本控制"就只是建议，不是控制。

### 交付了什么

| 模块                        | 内容                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------- |
| `server/gate.ts`            | 限流（滑动窗口）、日预算、单次上限、连续失败熔断 —— 全是纯函数                      |
| `server/store.ts`           | 任务落 JSON，写入用「临时文件 + rename」保证原子性                                  |
| `server/handler.ts`         | `Request → Response` 路由：`POST /api/jobs`、`GET /api/jobs/:id`、`GET /api/health` |
| `server/index.ts`           | `node:http` 适配器，把裸请求包成标准 `Request`                                      |
| `src/lib/providers/http.ts` | 前端新 provider，只认 `/api`，看不到任何密钥                                        |
| `scripts/dev.mjs`           | 一条命令同时起 API 和前端（vite 代理 `/api` → 8787）                                |

### 关键设计

1. **handler 不碰 `node:*`**：只写 Web 标准的 `Request` / `Response`。所以它现在能跑在 Node 上，
   以后能原样挪进 Cloudflare Pages Functions（`onRequest` 签名几乎一致），不用重写业务逻辑。
2. **闸门是纯函数**：`evaluateGate(state, request, limits, now)` 输入状态和当前时间，输出放行/拒绝与原因。
   这样"日预算用完"这类分支能在毫秒级单测，不需要真跑一个服务再等 24 小时。
3. **错误码比错误文案重要**：`ProviderError` 带 `code` 和 `retryable`。限流和额度耗尽不该给"重试"按钮——
   用户点十次也只是十次失败。UI 据此决定是"换个档位"还是"等一会儿"。
4. **成本以服务端为准**：前端估算只用于下单前预估，任务完成后用服务端结算的 `costYuan` 覆盖。

### 校验结果

- `tsc` / `biome`（0 告警）/ `vitest` **83 用例**（新增 gate 15 项、handler 11 项）/ `vite build` 全过
- 冒烟 19/19，且这次是真的经过服务端：先起 API，再由 vite 代理转发
- 手动验证过：`POST /api/jobs` → 轮询到 `succeeded` → `.data/jobs.json` 里能看到落库记录与结算成本

### 未做

- 没有鉴权：目前只防"手滑刷爆"，不防"故意刷爆"。真上线要加来源校验或登录
- 存储是单机 JSON：进程重启状态还在，但多实例不共享（换算成 Redis/KV 只需替换 `store.ts`）
- 真实 provider（混元生 3D）仍缺一块：卡在腾讯云实名认证

## 2026-10-25 · M4：多模型场景与摆放

对应方案 §7.5 与 §9 的 M4。目标是让"场景"这二个字真正落地 —— 单模型查看器是"看东西"，场景是"摆东西"。

### 交付了什么

| 模块   | 内容                                                                     |
| ------ | ------------------------------------------------------------------------ |
| 选中   | 点模型选中（悬停变手型）、点空白取消；选中后脚下出现贴地光圈             |
| 变换   | `TransformControls`：移动 / 旋转 / 缩放，再点一次同一模式收起 gizmo      |
| 容器   | `SceneObject[]`：复制、隐藏、删除、清空；新对象自动补进 X 轴空位         |
| 列表   | 侧栏「4 · 场景对象」：序号、位置(x/y/z)、缩放、显隐、复制、删除          |
| 持久化 | 位置/旋转/等比缩放全部写入 localStorage，刷新后场景原样恢复              |
| 快捷键 | Delete 删选中、Esc 取消选中、G/R/S 切移动/旋转/缩放（输入框内不拦截）    |
| 调试   | URL 带 `?debug=1` 时暴露 gizmo 的 axis / dragging 状态，供自动化验证拖拽 |

### 几个刻意的实现选择

1. **gizmo 挂在哪**：TransformControls 必须 attach 到具体的 `Object3D`。这里维护了一张
   `id → group` 的注册表，由 `ModelObject` 挂载时注册、卸载时注销。
   没有把 three 对象塞进 zustand —— 那会让 store 里出现不可序列化、会导致 React 重渲染的怪物。
2. **拖拽结束才写 store**：`onObjectChange` 每帧都触发，若每帧写 store 再 persist，
   localStorage 会被打爆。所以拖拽过程交给 three 自己改对象，`onMouseUp` 时才读回并落库。
3. **缩放必须收敛成标量**：TransformControls 的缩放是三轴的，拖单轴会得到扁模型。
   `readTransform` 用几何平均收成一个标量再夹到 0.2–4。
4. **取景只在集合变化时重算**：M1 的 AutoFrame 依赖 `objects`，一旦拖拽就会重新取景 ——
   相机跟着跳。现在加了"对象数量 / 已量到比例数量"的双计数守卫，拖拽时相机纹丝不动。
5. **允许同一个 GLB 放多次**：原来按 `glbUrl` 判重是为了修缓存重复入场景的 bug，
   但"同一款摆两个"是真实需求。现在只对**自动入场景**和**历史回看**判重，
   手动点「再加一个」就是真的再加一个。

### 这一轮踩的坑

### 三处与方案文档不一致（有理由，不是偷懒）

1. **去背景不用 `@imgly/background-removal`**，改为自研边缘种子泛洪（纯 Canvas）。
   - 方案里那套是浏览器内 ONNX 推理，首次要下约 40 MB 权重；国内网络这一步经常超时，  
     而"去背景"恰恰是质量提升性价比最高的一步，不能让它成为最脆弱的一环。
   - 泛洪方案零依赖、零下载、几十毫秒完成，对纯色/浅色背景产品图效果相当。  
     关键性质：只删**与边缘连通**且颜色接近背景的像素，主体内部的白色区域不会被误删  
     —— 这是它比全局色键抠图正确的地方，也有单测盯着。
   - 代价：背景有渐变、阴影、纹理时效果不如 AI 分割。此时会**保护性放弃**（`removedRatio>0.97`  
     判定为背景不可信），原图不做任何改动，UI 明确提示用户换一张背景干净的图。
2. **自动取景不用 drei 的 `<Bounds fit observe>`**，改为 `lib/fitCamera.ts` 自算距离。
   - 实测：模型经 Suspense 异步加载，`Bounds` 在挂载那一刻量到的是空盒子，  
     结果模型只占屏幕 16% 左右，画面大片空白。
   - 自算方案用"每个对象归一化后的比例 + 摆放位置"求并集包围盒，再按  
     `maxDim / (2·tan(fov/2))` 与 aspect 修正算距离。可单测、可解释、什么时候重算由我们决定。
   - 副作用：取景距离是我方逻辑，`<Bounds>` 那套自动 clip/near-far 保护要自己补，  
     已在同一段代码里设置 `camera.near/far`。
3. **场景容器提前做了**（`SceneObject[]`，可在 M4 之前就把多个模型摆进去）。
   - 方案 §7.5 要求"不要先做拖拽再做容器"，本次顺着这个顺序：容器 + 选中高亮 + 删除先到位，  
     `TransformControls` 拖动留给 M4。

### 过程中修掉的三个真 bug（都是先跑起来才暴露的）

| Bug                          | 现象                     | 根因与修法                                                                                                                                  |
| ---------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 归一化把模型挪到半空         | 底面 y = 497.5 而不是 0  | 按"绕世界原点缩放"换算平移量。实际缩放绕物体自身原点，必须**缩放后重新量包围盒**再平移                                                      |
| 去背景的兜底会毁图           | 放弃分支执行后原图变空白 | 泛洪直接在 rgba 上改 alpha，判定放弃时无法回滚；且用 `clearRect`+`drawImage(自己)` 恢复更是错的。改成两阶段：先算掩码，确认应用后再写 alpha |
| 同图重生成出现两个一样的模型 | 场景里并排两个相同 GLB   | 去重缓存命中后拿到同一个 `glbUrl`，而自动入场景按"任务 id"判重。改成按 `glbUrl` 判重                                                        |
